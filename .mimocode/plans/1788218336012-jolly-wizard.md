# Plan: What else is broken besides features 4, 8, 9

## Context

The user already knows PRD features 4 (Budget & Sponsorship), 8 (Volunteers), and 9 (Incidents) are broken — they have only DB migrations (`007_create_budget.sql`, `010_create_volunteers.sql`, `011_create_incidents_*.sql`) and "Coming Soon" placeholder pages (`client/src/app/routes.tsx:253-267`); no backend modules exist for any of them.

The question: are there **other** bugs? A read-only audit was done. Result: 199 tests pass (131 server, 68 client) and both typechecks are clean, so the breakage is not in unit-tested code paths. Three real bugs were found outside features 4/8/9, plus several minor issues.

---

## Critical bugs (will throw at runtime)

### Bug 1: `checkin.repository.ts:39` — `ON CONFLICT DO NOTHING` with no target on a table that has 2 unique constraints

```ts
// server/src/modules/checkin/checkin.repository.ts:38-43
"INSERT INTO check_ins (event_id, user_id, itinerary_item_id, method, checked_in_by) VALUES ($1, $2, $3, $4, $5) ON CONFLICT DO NOTHING RETURNING *"
```

- `check_ins` has the PK `id` (migration 006:41) plus the partial-expression unique index `idx_check_ins_event_user_item` (migration 016:27-32).
- With 2 unique constraints and no target, Postgres raises `42P10` ("there is no unique or exclusion constraint matching the ON CONFLICT specification") on **every** call.
- Called from `checkin.service.ts:14` (manualCheckin), `:36` (qrCheckin), `:56` (bulkCheckin) — the entire check-in flow is broken.
- CLAUDE.md:70 explicitly warns about this: *"an `ON CONFLICT (...)` target that doesn't match a real unique index throws PG `42P10` at runtime on every call"*. This is exactly the case it warned about.
- **Why tests pass**: the checkin module has no `checkin.service.test.ts`. Only the broader service is mocked downstream.

**Fix**: add the matching index target — `ON CONFLICT (event_id, user_id, COALESCE(itinerary_item_id::text, '')) DO NOTHING`. Or, since `bulkCreateEligible` already pre-checks for duplicates with `NOT EXISTS`, the simplest fix is to drop `ON CONFLICT` entirely (pre-check is sufficient for the user-initiated path; bulk path uses `NOT EXISTS`).

### Bug 2: `certificates.repository.ts:71, 121` — same `ON CONFLICT DO NOTHING` bug

```ts
// server/src/modules/certificates/certificates.repository.ts:68-74
`INSERT INTO certificates (event_id, user_id, certificate_type, status, verification_code, metadata)
 VALUES ($1, $2, $3, 'eligible', $4, $5)
 ON CONFLICT DO NOTHING RETURNING *`
```

- `certificates` has PK `id` (migration 011:23-26) plus `idx_certificates_event_user_type` on `(event_id, user_id, certificate_type)` (migration 016:14).
- Same PG `42P10` failure on every `createCertification` and `bulkCreateEligible` call.

**Fix**: `ON CONFLICT (event_id, user_id, certificate_type) DO NOTHING RETURNING *`.

## High bugs (functional / multi-tenancy)

### Bug 3: `notifications.service.ts:24-54` — three notification helpers are dead code

`notifyTeamRequest`, `notifyTeamRequestResult`, `notifyCheckinReminder` are defined but no module imports `notificationsService` (`grep "notificationsService\." server/src` returns zero hits outside the notifications module itself).

- Practical effect: team join requests send no notification to the organizer; accept/decline decisions send nothing back to the requester; check-in reminders never fire.
- The whole `NotificationsPage` UI will always show "No notifications yet" against a populated events list — which looks like a UI bug but is actually because nothing creates rows.

**Fix**: wire the calls into `teams.service.ts` (`notifyTeamRequest` when a request is created; `notifyTeamRequestResult` when the organizer responds) and into a scheduled check-in reminder path (the latter is non-trivial — defer or use a `pg_cron`).

---

### Bug 4: `notifications.repository.ts:28-49` — `markAsRead` / `delete` are not event-scoped

```ts
// server/src/modules/notifications/notifications.repository.ts:28-34
"UPDATE notifications SET read_at = NOW() WHERE id = $1 AND user_id = $2 AND read_at IS NULL RETURNING *"
```

- Route mounted at `/api/v1/events/:eventId/notifications/:notificationId/read` (notifications.routes.ts:29-34); the `:eventId` is in the URL but never reaches the repository SQL.
- A user with membership in event A who happens to own a notification in event B can mark-as-read or delete it through event A's URL. This is a multi-tenancy violation per CLAUDE.md:55-58 ("cross-event ID injection is the recurring vulnerability class").
- Minor variant in `getScoreById`-style is fine; notifications don't follow the pattern.

**Fix**: add `AND event_id = $N` to both queries (eventId comes from `req.params.eventId`).

## Medium / latent

### Bug 5: Duplicate-prefix migrations + lexicographic sort

`server/src/db/migrations/018_itinerary_room_speaker_materials.sql` and `018_venue_location_positions.sql` share number `018`; `019_checkin_checkout_tracking.sql` and `019_temporary_admins.sql` share `019`.

- `run-migrations.ts:15` uses `.sort()` (lexicographic). For the current four files the order happens to work because they're all idempotent ALTERs touching unrelated tables, but the dependency model is fragile.
- Migration names sort by `_` (0x5F) > digits, so `018_iti...` < `018_ven...` < `019_che...` < `019_tem...` < `020_not...` — stable but coincidental.
- Latent risk: any future migration in the 018/019 slots that depends on another's output will silently misorder.

**Fix**: rename to `018a_...`, `018b_...` or bump to `021_...` / `022_...` and keep `run-migrations.ts:15` on `.sort()`. (Numeric prefix sort would require padding to 3+ digits or a custom comparator.)

## Low / minor

### Bug 6: `event-members.routes.ts:9-13` — `/me` lacks `authenticate` middleware

```ts
// server/src/modules/event-members/event-members.routes.ts:9-13
router.get("/me", eventMembersController.getMyRole);
```

The controller at `event-members.controller.ts:73` throws `ValidationError("Authentication required")` (a 400) when `req.user` is missing — instead of `authenticate` returning a proper 401. Functionally fine when everyone hits it logged-in, but produces wrong status codes for unauthenticated probes.

**Fix**: add `authenticate` to the route chain.
